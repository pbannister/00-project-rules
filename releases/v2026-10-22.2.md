# Release v2026-10-22.2 — evidence

Impact: internal

## What changed

The release gate and the documentation. No file in `MANIFEST` changed, so a
project pinning this version receives byte-identical rules to `v2026-10-22.1`.
That is what `Impact: internal` asserts, and it is checked rather than believed:
the gate diffs `MANIFEST` against the previous tag and refuses the claim if any
shared file moved.

## Why a second release on the same date

The initial build-out. The first version established the extraction; this one
adds the house rules the repository is meant to run under — branchless, one
release a day, stated impact. Both belong to the repository's own tooling, which
a project never sees, so folding them into the first release would have
misdescribed it.

This is the exception `--same-day` exists for, not the cadence. Once a project
pins a version, a second same-day release is reserved for a correction that
cannot wait; routine changes wait for the next day, because a tag that moves or
multiplies is a tag a project cannot reason about.

## Machine-checkable evidence

`make test` at the tag: five tests, including the vendor/check round trip and the
end-to-end vendor into `00-project-skeleton`.

| Gate | Behaviour it enforces |
|---|---|
| branchless | refuses a detached HEAD, or more than one branch |
| one release a day | refuses a second tag on the same date without `--same-day` |
| impact | refuses a missing or unknown `Impact:`, and refuses `internal` when `MANIFEST` changed |

## Behavioral evidence

Not applicable, and that is exactly what `internal` is for: no shared rule
changed, so no eval case can behave differently. An `additive` or `breaking`
release records its eval run in its own file; a `wording` release states why no
behavior moved.
