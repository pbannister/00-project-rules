# Release v2026-10-22.13 — evidence

Impact: additive

## What changed

The shared test helper gained an optional, project-owned extension file. No rule
changed, and a project that does not use the extension sees no difference.

## Why

Adopting `gnome-appimage-integration` looked like the easiest adoption yet — six
findings — and then nineteen of its thirty-seven tests failed at once.

The cause was one file. Its `tests/lib/test_helpers.sh` is a 79-line helper with
project-specific additions (`build_program`, `build_synthetic_appimage`,
`DIRECTORY_BUILD`). The shared set classifies that path as vendored, so the
adoption's `--force` replaced it with the 35-line shared version and every test
that used the additions failed.

The failure mode is the dangerous kind: the vendor reports success, the validator
reports nothing, and the damage only appears when the suite runs — or worse, does
not run.

## The fix, and the one that was rejected

A project fork of a vendored file cannot survive an upgrade; that is the whole
reason the rules forbid it. Extending the shared helper into a superset was
rejected: it would put an AppImage builder and a program builder into every
project, which is the same "shared material assumes the template's inventory"
mistake this library has now paid for five times.

So the shared helper defines the four functions the vendored tests need and then
sources `tests/lib/project_helpers.sh` when it exists. A project's additions live
there, untouched by any upgrade.

## Machine-checkable evidence

- `tests/lib/test_helpers.sh` in the rules repository: sources the extension file
  only when present, so a project without one behaves exactly as before.
- `gnome-appimage-integration`: after the split, `make test` is green across 37
  tests, including the twenty that had failed.
- Library suite: 9 tests.

## Behavioral evidence

Not applicable: no instruction an agent follows changed. This is test scaffolding,
and what it changes is whether a project's suite can run at all after adopting.
