# Release v2026-10-22.3 — evidence

Impact: additive

## What changed

One line of the contract, plus the test that decides when faithfulness is
asserted. No existing rule reverses, so an adopting project needs no eval run:
`rules.lock` becomes a permitted root file, and nothing else moves.

## Why the pilot found it

Pinning `00-project-skeleton` — the step after extraction — failed its own
validator. Section 7 of `prompts/01-contract.md` enumerates the canonical
root-level files, and `rules.lock` was not in the list, so
`tests/09-prompt-contract.sh` reported:

```
root file is not permitted by contract section 7: rules.lock
```

That is the validator doing its job on a real project, which no test inside
`00-project-rules` could have discovered: the rules repository holds only the
shared layer, so it cannot itself be a project. The pin is what made the gap
observable. Every project that adopts these rules will carry `rules.lock`, so the
file belongs in the canonical list rather than in each project's local
declaration.

## The second defect: a release deadlock

`tools/tests/04-skeleton-integration.sh` asserted that vendoring the current
version into the skeleton changed nothing. That is true only once the skeleton
pins the current version — and the skeleton can only adopt a version after it is
released. Any release that changes a shared rule therefore failed its own gate.

The test now asserts faithfulness exactly when it is meaningful (skeleton pins
the version under test), and always asserts the property that matters: a complete
project with this version vendored passes `tests/09-prompt-contract.sh` and
`tests/13-corpus-coverage.sh`.

## Machine-checkable evidence

- `make test` in this repository: five tests.
- `tests/09-prompt-contract.sh` green against a copy of the skeleton with this
  version vendored, which is the check that failed at v2026-10-22.2.
- Skeleton `make test`: green, including the new `tests/04-rules-pin.sh`.

## Behavioral evidence

Not applicable: the change permits a file and alters no instruction an agent
follows, so no eval case can behave differently. An `additive` change to a rule's
*wording* would need the eval run recorded here; this one changes no wording.
