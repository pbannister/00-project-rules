# Release v2026-10-22.9 — evidence

Impact: additive

An adopter runs `rules-vendor.sh --prune` once and updates any local reference to
the renamed file. Nothing an agent follows changed meaning.

## What changed

1. **A rename.** `prompts/common/02-universal-rules.md` is now
   `prompts/common/01-universal-rules.md`, filling the slot left when
   `01-requirements.md` was retired. The content is byte-identical; every
   reference in the shared set is updated.
2. **`--prune`.** A renamed or dropped shared file leaves a copy behind, and two
   copies of a rule set disagree the moment either is edited — the validator
   reports the leftover as a duplicate. The vendor can now remove it, opt-in.
3. **`## Requires`.** Each eval case declares the files a project must carry, and
   `rules-eval-task.sh` refuses a case whose prerequisites are absent.
4. **`documents/eval-portability.md`.** The scope for rewriting the cases, which
   is a separate task and a separate decision.

## Why

The rename was requested. Two consequences were not obvious until it was done:

- **A stale file is a second source of truth.** The old path stayed in each
  project, and the validator then reported the same rule family twice —
  `duplicated in prompts/common/02-universal-rules.md`. Hand-deleting in thirteen
  projects is a rule learned by failing at it, so the vendor gained `--prune`.
- **Local files name shared paths too.** The glossary in every project cites the
  universal-rules file, and the rename broke that citation. The validator caught
  it (`reference does not exist`), which is the correct place: a rename is
  mechanically visible, not silently tolerated.

`## Requires` came from the eval attempt in `09-language-elseon`, which produced
no data because the case operated on `scripts/status.sh`, a file that project has
never had.
